- **P0 correctness risk, confirmed deliberate current policy — acceptance is evidence-only.** `server/solveAcceptancePolicy.js:1-15` explicitly defines compatibility policy v1: it rejects only structurally unusable candidates. Every structurally usable candidate is accepted even when server verification reports a contradiction (`reason: structurally_usable_with_contradiction_evidence`), with `mathematicalCorrectness: not_established`, and neither repair nor escalation requested. `server/solveCandidateLifecycle.js:5-10,17-27` attaches that server-side verification/acceptance metadata after structural assertion; verification is evidence, not an acceptance gate. - **Confirmed — structural checks do cover a nonempty/renderable final answer and every step, but not mathematical truth.** `server/solveCandidateStructure.js:141-160` requires visible final-answer math and strict generated-LaTeX validation; `:163-230` requires at least one step and validates each chosen math field. This boundary is appropriately described as structural/renderability at `:62-65,100-104`.
- **Confirmed routing weakness — complexity classification currently cannot select a stronger initial role.** `server/solverRouting.js:31-39` always returns `role: "solver"`, including repair/escalation-tier classifications. `server/app.js:163-172` therefore always reports the canonical-solve model as the selected initial model; its `routeSource` test can never become `difficulty-based`. For any cached/local/multi-attempt/escalated result without an explicit model this logs the global/default model rather than an observed provider model; the affected callers are identified below.
- **Confirmed OCR review binding.** `server/ocrSolvePolicy.js:31-99` treats validation evidence/structural disagreement as review input and accepts a confirmation/edit only when the action kind and `canonicalInputHash` match; `:102-112` produces a 409 `OCR_REVIEW_REQUIRED`. It does not independently block merely on a low numeric confidence unless the canonical findings are critical/structural, matching its stated design at `:24-29`.
- **Confirmed internal auth preservation.** `server/app.js:130-149` explicitly reconstructs internal requests with original headers because spreading `IncomingMessage` would lose authorization/cookies.
- **Confirmed security/persistence boundary.** `server/userData.js:401-436` persists explanations only when the database is configured and a verified Clerk identity exists, then keys the insert through the upserted server-side user. Session update/delete SQL scopes by both `user_id` and session id (`server/userData.js:319-398`).
- **Confirmed non-progressive recovery defect — the repair branch is unreachable.** `server/app.js:1054-1063` classifies every failure as `response_generation_failure`, regardless of whether a parsed candidate exists. The ordinary JSON solve then immediately rethrows that category at `:3049-3052,3084-3086`, so the repair call at `:3087-3156` cannot run. The exported candidate ranking/escalation helpers are definitions only (`:957-1161`; no production call sites), and this path contains no fresh escalation call. Provider transport retries can still occur inside `openai.js`, but candidate-quality repair/model escalation do not occur on this non-streaming path.
- **Confirmed progressive recovery is a separate, bounded policy.** Before any authoritative step is published, `server/progressiveRecoveryPolicy.js:37-67` permits at most one retry, one repair when a complete repair candidate exists, and then escalation for specified repeated structured-output failures; it refuses recovery after a prefix is published and caps provider attempts at four. `server/app.js:2640-2700` applies those decisions and changes `attemptType`, which changes the selected role/model. Once a step is published, the prefix is immutable (`server/progressiveStepValidation.js:111-118`) and later failure is terminal rather than silently replacing streamed work.
- **Confirmed timeout/abort split.** Non-stream provider calls get per-attempt `AbortSignal.timeout(...)` and a shared wall-clock deadline (`server/openai.js:962-1025,1027-1034`), with up to three attempts for solver/canonical solve and two for other roles (`:339-342`); transient transport errors and HTTP 408/409/429/5xx are retried (`:691-709,829-849,1014-1089,1197-1275`). Their retry delay itself is not clipped to the remaining solve budget (`:1088,1275`), so it may overshoot before the next loop notices exhaustion. Progressive streaming composes the client-disconnect signal with the timeout using `AbortSignal.any` (`:1384-1403`) and retries only before provider bytes are seen (`:1531-1552`); `server/app.js:2370-2379` aborts it when the response closes/request resets. The ordinary JSON path does not pass a request/client signal into `createMathExplanation` (`server/app.js:3006-3030`).
- **Confirmed observed model attribution is available for progressive output.** Provider stream events update the model from `event.response.model` (`server/openai.js:1407,1449-1455`) and return it (`:1518-1529`); progressive terminal/cache metadata use that observed model (`server/app.js:2583,2617-2638,2710-2726`). This contrasts with the default-model fallback in `logExplanationSource` noted above.
- **Confirmed hover/pin model logs are misattributed; compare/follow-up only coincide with the fallback today.** All four callers omit `model` (`server/app.js:3863-3870,3988-3995,4101-4108`), so `logExplanationSource` falls back to `getOpenAiModel()`—the solver role (`server/openai.js:344-346`). Live hover/pin calls actually select their own paths/models (`:2790-2808`), making that attribution wrong. Compare and follow-up currently use the solver model (follow-up merely applies the pinned timeout role; `:2779-2787`), so their live-call field happens to agree, while local fallback still names a model despite no provider call. The top-level log field does not consult per-model usage tags.

Both defaults are `gpt-5.6-sol` (`server/openaiModels.js:16-24,27-28`), so escalation is suppressed even though the escalation role requests high reasoning while canonical solver uses medium (`:78-83`). A same-model/higher-reasoning fresh attempt is therefore not considered available; only configuring a different escalation model id activates it.

- **Confirmed final-answer schema/normalization behavior.** Full text/image schemas require one string `finalAnswerLatex` (`server/mathExplanationSchema.js:107-123,141-165`); compact retry has no separate final field and promotes the last returned step (`:125-139,1406-1415,1460-1473`). Physical multiline full answers are converted to one `gathered` expression when every line parses (`:652-666`). Although the validator identifies multiple physical lines, explicit line-break commands, derivation arrows, prose, and unrelated equations as final-answer contract findings (`server/generatedLatexValidation.js:308-341`), it records these as warnings (`:383-389`), while collection rejects only `valid === false` (`:423-428`). Thus those final-answer shape rules are diagnostic rather than acceptance gates; the enforced boundary remains nonempty/visible/renderable structure.
- **Confirmed candidate-retention boundaries.** The full-response compact retry keeps accumulated usage but does not retain candidate 1 for fallback: candidate 1 must have thrown during parse/normalization before retry (`server/openai.js:2472-2546`), and a compact provider/parse failure is rethrown with `previousUsableCandidate: false` (`:2547-2644`). A successful compact candidate replaces it (`:2646-2691`). Separately, after an ordinary candidate has been structurally accepted, annotation failure preserves and returns that accepted pre-annotation candidate (`server/app.js:3160-3190`). Progressive mode never replaces an already published prefix and persists a partial prefix on terminal failure (`:2640-2700,2767-2785`).
- **Confirmed bounded-verifier edge — the final answer is omitted at 32 or more steps.** Verification builds all step fields, appends the final-answer field, then evaluates only `fields.slice(0, 32)` (`server/verification/solutionVerifier.js:4,18-24`). Therefore a 32-step candidate's final answer is field 33 and receives no final-linked check; only an inconclusive coverage-limit record is added (`:57-64`). Provider solve schemas currently cap steps at 10 (`server/mathExplanationSchema.js:107-139,141-165`), so ordinary provider output cannot hit this edge, but the final structural/lifecycle verifier itself has no equivalent 31-step guard and can be called on other candidates.
- **Confirmed OCR trust weakness — hash binding is not a server-authentic receipt.** The server recomputes the submitted canonical problem and requires the action kind/hash to match it (`server/app.js:3525-3541`; `server/ocrSolvePolicy.js:53-74`), but both `extraction.extractionValidation` and `reviewAction` come from the client request (`server/app.js:3508-3524`), and the frontend itself constructs the matching review action (`src/api/mathClient.js:463-483`). No signature, nonce, stored extraction record, image hash binding, or server-only receipt is verified. A modified client can therefore remove critical/structural findings for a `direct` solve or mint a matching confirmed/edited action. The image hash is carried as metadata/cache reference only (`server/app.js:3544-3548,3553-3578,3605-3609`).
- **Confirmed production auth parity, with a local-development mismatch.** Image extraction requires verified Clerk identity directly (`server/app.js:3338-3348`), and OCR solve delegates through a header-preserving internal request to the shared solve boundary (`:3591-3633`), which verifies identity in production (`:2829`; `:1670-1684`). Typed solves use that same shared boundary. In non-production only, typed/shared solves accept a synthetic local identity while `/api/extract-image-problem`, hover/pin, and compare routes call `requireClerkIdentity` directly; local auth behavior is therefore not route-parity (`:1670-1684,3338-3348,3700-3712,3904-3914`). Clerk tokens are cryptographically verified and optional authorized-party checks are passed to Clerk (`server/usageIdentity.js:197-279`).
- **Confirmed persistence is optional and solve-save durability is best effort.** PostgreSQL tables enforce unique Clerk users, user-owned explanation/session foreign keys, and indexed history/session ordering (`db/migrations/002_user_profiles_and_history.sql:3-31`; `003_user_sessions.sql:1-11`). Ordinary solves launch the explanation save without awaiting it and immediately report `saveStatus: "pending"` (`server/app.js:3274-3307`); progressive success and partial-failure saves are likewise unawaited (`:2717-2726,2767-2785`). Rejections are observed/logged, but process termination can lose an acknowledged pending save. Development schema/database fallback returns empty history and synthetic session success objects without durable storage, including `deleted: true` (`server/userData.js:188-225,228-317,319-398`); production does not take that fallback (`:8-20`).
- **Confirmed usage reservation is not atomic across checks/metrics.** Quota counts are read and checked first (`server/usageLimits.js:554-731`), then eight daily/monthly user/global counters are incremented sequentially (`:743-793`). Concurrent requests can pass the same pre-check; a later increment failure can leave a partial reservation. Redis makes each single-key increment+expiry pipeline atomic only for that key (`:140-189`), not the whole reservation. The local JSON store performs unlocked read/modify/direct-write (`:222-278`), so concurrent processes/requests can lose updates and interruption can leave invalid JSON.
- **Confirmed usage settlement is awaited, unlike explanation persistence.** Canonical success awaits reservation settlement before caching/responding (`server/app.js:3217-3223,3242-3244`), progressive success awaits settlement before cache/final events (`:2717-2726`), and the lazy/compare handlers also await settlement (`:3832-3837,3967-3972`). This is fail-closed for a wholly unavailable usage store, but the multi-key reservation/settlement operations above have no rollback for partial success.
- **Confirmed failed-call accounting gaps.** Canonical solves attempt to settle known failure usage/provider-call counts and release only failures before a provider call (`server/app.js:1977-1989,3223-3239`). In contrast, image extraction, hover/pin, and compare catch paths unconditionally release reservations (`:3471-3477,3838-3844,3973-3979`), even though provider errors may follow billable work. Production follow-up failure also reaches an unconditional release (`:4052-4070,4092-4098`). Where a provider call count exists but no usage payload exists, canonical failure settlement charges requests but settles token/cost deltas to zero (`:1957-1989`), undercounting unknown billable tokens/cost. Cache hits and same-process in-flight duplicates do not reserve again (`:2873-2902,2957`; `:3759-3780,3874`; `server/duplicateRequests.js:1-22`); this is deliberate non-charge behavior, but both cache/dedup are process-local memory (`server/explanationCache.js:3-53`).
- **Confirmed successful non-stream transport retries are not reflected in request-count settlement.** Transport diagnostics track every HTTP attempt (`server/openai.js:1014-1018,1046-1059,1103-1109,1206-1261`), but successful response metadata stores `providerCallCount` as `successfulProviderResponses` rather than `transportAttempts` (`:1093-1095,1156-1158`), and `createMathExplanation` hard-codes one logical call (two after compact retry) (`:2468-2472,2588-2590`). Consequently a solve that succeeds after one or two retryable provider responses/errors settles one request for that generation, while progressive accounting does count its outer provider attempts.
- **Confirmed security controls and debug-route risk.** JSON/multipart bodies are size bounded, image MIME is allowlisted, and file signatures are checked (`server/app.js:1503-1555,1734-1793`); API secrets remain in server-only request headers (`server/openai.js:306-319,462-467`), and production 5xx responses use public messages (`server/app.js:1400-1417`). However, when `ENABLE_OPENAI_DEBUG_ROUTE=true` in production, `/api/debug/openai` is unauthenticated and performs a provider call while returning runtime/env/provider error details (`server/app.js:2297-2329,4223-4226`). `/api/health` is also unauthenticated and discloses model/auth/env-loading configuration including process cwd and loaded env filenames (`server/app.js:2279-2294`; `server/env.js:44-55`).
