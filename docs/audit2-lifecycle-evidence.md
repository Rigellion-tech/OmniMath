# Audit #2 lifecycle evidence — 2026-09-28

Audit-only working evidence. No application fixes, commits, browser launches, or provider calls. The dirty working tree is the baseline.

## Scope and status

- Complete: Home solve/OCR request identity, session/version stale acceptance, progressive presentation/recovery, ExplanationPanel follow-up/pin/provenance lifecycle, worker cancellation/fallback, post-measure stationary-pointer reconciliation, semantic role vocabulary, and focused test-oracle review.
- Static/code-and-test audit only. No provider calls or browser run were made, so explicitly identified timing/layout cases remain code-supported risks rather than runtime reproductions.
- Findings are classified as **confirmed invariant**, **confirmed weakness**, or **open risk**. An open risk is not a reproduced defect.

## Initial invariants to verify

- Every asynchronous solve/OCR/follow-up/pin result must be accepted only by the request, problem/session, and solution version that launched it.
- Abort must prevent state acceptance even when transport completion races with cancellation.
- Progressive state must not overwrite a newer request, survive an invalid recovery, or present provisional output as accepted final output.
- Pinned/follow-up explanations must retain source provenance and remain scoped to the solution version that created them.
- Worker responses and fallback work must be correlated to the active render generation; stale work must be ignored and cancellations must settle callers.
- Pointer ownership must be reconciled after authoritative measurement even if the pointer is stationary.

## Evidence log

- Checkpoint confirms lifecycle coverage did not survive the prior runtime transition and must be redone (`docs/audit2-checkpoint.md`).
- Repository has extensive pre-existing modifications and untracked progressive-rendering files; this report does not treat HEAD as the audit baseline.
- **Confirmed invariant — session/request acceptance:** `Home.jsx:363-406` creates a monotonically revised operation per origin session and rejects results when the origin session is absent or the operation id/revision is no longer current. Typed completion/error/history paths re-check that ownership (`PrimaryMathComposer.jsx:184-240`; `Home.jsx:711-873`). Image extraction, direct solve, and reviewed solve also check both the component-local operation and Home ownership before accepting results (`ImageUpload.jsx:446-451,558-568,625-635,696-780`). Session switching alone deliberately does not invalidate the origin operation, so work can complete into its origin session.
- **Confirmed invariant — progressive acceptance:** `Home.jsx:1110-1151` requires the event session to exist and its request/attempt ids to equal the current operation before feeding the reducer. Session commits use `strictTarget: true`; status is stored per session. Duplicate wire `solve_started` is the only specially acknowledged duplicate.
- **Confirmed weakness — deletion/reset cancel transport incompletely:** deleting a session removes progressive state but neither invalidates `activeOperationsRef` nor reaches the typed/image abort controller (`Home.jsx:676-709`). A successful deletion makes later acceptance fail because the session is absent, but provider work continues; if deletion fails and the old session is restored before completion, the still-current operation can again pass acceptance. Home reset invalidates ownership and typed reset aborts its controller, but a reset initiated outside the image review does not reach ImageUpload's session-keyed controller (`Home.jsx:631-646`, `PrimaryMathComposer.jsx:245-250`, `ImageUpload.jsx:435-444`). Classification: lifecycle/resource weakness; stale restoration race is code-supported but not runtime-reproduced.
- **Confirmed weakness — typed request becomes unobservable after session switch:** `PrimaryComposerSession` is keyed by session (`PrimaryMathComposer.jsx:340-349`). Its unmount cleanup only flips `mountedRef`; it does not abort, and the new instance has no reference to the old request (`PrimaryMathComposer.jsx:98-115`). Completion remains safely routed to the origin session, but switching away and back removes the cancel control/loading state even while Home still marks that session as generating. Classification: cancellation/UI ownership weakness, not stale-write acceptance.
- **Confirmed invariant — OCR review preserves operation identity:** the extraction and edited review remain keyed by origin session, and initial reviewed solve reuses the extraction operation; retries create a new Home operation only after an error (`ImageUpload.jsx:392-451,696-721`). The submitted payload is rebuilt from reviewed display text and tagged `ocr-reviewed` (`ImageUpload.jsx:723-754`).
- **Confirmed invariant — follow-up ownership and ordinary cancellation:** each follow-up is identified by request id, conversation id, and target revision; both the live owner and the server echo must match before an answer is accepted (`ExplanationPanel.jsx:1093-1159`; `followupLifecycle.js:49-64,92-105`). A conversation/revision change resets the reducer, aborts the old controller, and nulls its owner; unmount does the same, while response/error paths re-check mount and ownership (`ExplanationPanel.jsx:1014-1045,1135-1171`). Failed or normally aborted requests remove the optimistic user turn and restore the exact question (`followupLifecycle.js:106-127`).
- **Open risk — follow-up timeout success guard is implicit in transport semantics:** the timeout only sets `timedOut` and aborts the controller (`ExplanationPanel.jsx:1111-1115`). The success path after `await` does not explicitly test `timedOut` or `signal.aborted` before the mount/owner/echo checks and success dispatch (`ExplanationPanel.jsx:1117-1159`). Native fetch normally rejects on abort, and an already-settled response continuation ordinarily runs before the later timer, so this audit did not establish a reachable browser race. A custom/nonstandard transport or boundary ordering that fulfills after observing abort would still pass the component guards. The reducer tests cover a synthesized `request_failed` timeout, not transport timing (`followupLifecycle.test.mjs:56-74`).
- **Confirmed invariant — immutable occurrence provenance:** snapshot construction detaches bounded step evidence and the current step, clones target/ancestor identity, computes a solution revision, and recursively freezes the result (`explanationProvenance.js:48-85,89-161`). Conversation identity distinguishes problem/step/target/range and target revision additionally binds solution revision (`explanationProvenance.js:155-170`). The server validates version, target/step consistency, range, confidence, and evidence shape before prompting, treats prior model text as non-authoritative, and explicitly instructs uncertainty on missing/conflicting evidence (`followupProvenance.js:74-167,242-304`).
- **Confirmed invariant — local follow-up fallback remains occurrence-grounded and uncertainty-aware:** it names the selected occurrence and saved current-step math, attributes prior pin text only as what the earlier explanation “says,” and explicitly refuses to establish a deeper origin when confidence is insufficient (`followupProvenance.js:307-322`). It does not synthesize a derivation from the untrusted prior explanation.
- **Confirmed weakness — pin cache/dedup identity is not solution-version scoped:** the lazy cache key includes problem id, step id, target/text, selected-step/parent/title context hash, and level, but not the provenance `solutionRevision` or operation/attempt revision (`ExplanationPanel.jsx:203-225`). Module-wide pin caches and in-flight dedup use only that key (`ExplanationPanel.jsx:65-70,322-339,469-475,650-768`). A reachable progressive path is: pin an accepted early step, close it, allow later accepted steps to extend the same problem id while leaving the selected step unchanged, then re-pin the same occurrence; the key components remain equal and the older pin explanation is reused. UI duplicate prevention while the first pin remains open is otherwise exact for reference type/id/step (`HoverContext.jsx:496-500,1493-1536`).
- **Confirmed invariant — lazy hover/pin UI acceptance is double-gated:** owner effects compare request id/cache key/mode/target, resolved data must match target and step, and the reducer independently rejects success/failure for a request no longer present (`ExplanationPanel.jsx:611,683-760,813-927`; `hoverTargetIdentity.js:231-236`; `lazyExplanationLifecycle.js:27-35,85-115`). In particular, a lazy timeout first clears the reducer's current request, so a transport completion queued after it cannot overwrite the timeout state even though the owner ref is cleared only in final cleanup (`ExplanationPanel.jsx:782-801,861-927`). Pin failure may display a hover-cache fallback only after the same target/step predicate succeeds (`ExplanationPanel.jsx:288-295,550,754-759`).
- **Confirmed weakness — long-solution compaction can drop the selected step from ordered evidence:** the client intentionally centers a 64-step evidence window around the selected step (`explanationProvenance.js:60-67,108`), but server normalization unconditionally keeps only its first 48 entries (`followupProvenance.js:147-156`) before the later 12-step selector tries to preserve the origin (`followupProvenance.js:208-235`). A direct Node probe with 64 entries and origin `step-55` produced 48 normalized entries, no `step-55` in normalized or prompt evidence, while `origin.currentStep.id` remained `step-55`; the prompt selector returned only steps 0, 1, 6, 12, 18, 24, 30, 36, 42, 46, and 47. Existing long-distance server coverage uses only 40 entries and therefore does not exercise this boundary (`followupProvenance.test.mjs:92-117`); the client test verifies only the pre-server 64-step window (`explanationProvenance.test.mjs:69-87`).
- **Confirmed invariant — worker results are request-correlated and cancelled owners cannot publish:** every semantic render receives a unique id; messages with no pending owner are ignored, and cancellation removes the id and suppresses `finish` (`semanticRenderClient.js:21-25,36-45,57-61`). A worker failure terminates the shared worker, marks it unavailable, moves every still-pending request to the same serializer on the background queue, and clears the pending map (`semanticRenderClient.js:10-16,26-56`). Main-thread fallback cancellation removes its keyed queued callback (`mathGeometryScheduler.js:39-53,105-117`).
- **Confirmed weakness — cancellation does not remove already-posted worker computation:** cancelling deletes only the main-thread pending-map entry; no cancel message is sent and the shared worker serializes every posted job to completion (`semanticRenderClient.js:49-60`; `semanticRender.worker.js:3-10`). Stale results are safely ignored, but rapid render churn can leave obsolete worker jobs ahead of current work. Classification: bounded lifecycle/resource and latency weakness, not stale-state acceptance. Tests prove stale publication suppression and construction-failure fallback, but not queued-job cancellation or cancellation of a scheduled main-thread fallback (`semanticRenderClient.test.mjs:4-42`).
- **Confirmed invariant — stationary pointer can acquire a target after measurement:** both authoritative measurement paths call ownership reconciliation and then a post-measure pointer resolver (`MathChunk.jsx:4281-4289,5343-5351`). When there was no resolved target, the resolver uses the saved pointer, confirms it is still over the connected chunk, reruns semantic resolution against the new snapshot, and activates the target without requiring another mousemove (`MathChunk.jsx:6063-6088`).
- **Open risk — stationary pointer does not re-rank a still-containing old target:** `reconcileMeasuredHover` retains and re-anchors the current semantic id whenever its new rectangle still contains the pointer, then `resolvePointerAfterMeasureRef` immediately returns because an id remains active (`MathChunk.jsx:4012-4049,6063-6065`). Thus, if authoritative measurement introduces a more specific overlapping owner while the provisional/old target still contains the stationary pointer, the production scorer is not rerun until movement. This audit did not reproduce the required provisional-to-authoritative overlap in a browser. The hover-ownership unit tests cover retention/departure/DOM replacement, not post-measure overlapping-target re-ranking (`hoverOwnership.test.mjs:34-112`).
- **Confirmed weakness — semantic role vocabularies disagree at an ownership boundary:** the renderer treats `evaluation`, `evaluatedExpression`, and `evaluationCondition` as annotatable groups while hiding `evaluationBar` as syntax owned by a parent (`semanticMathRenderer.js:6-33,219-243`; `mathSemanticTree.js:1411-1460`). The hover aggregate/internal-gap vocabularies do not include those evaluation roles, while `evaluationBar` is explicitly ineligible (`semanticHitboxes.js:298-325,372-395`; `MathChunk.jsx:1247-1271`). A direct semantic-tree probe of `\left.x^2\right|_{0}^{1}` confirmed `evaluation` is a non-eligible, non-aggregate group and `evaluationBar` is a non-eligible leaf; only its numeric condition/superscript children were eligible. The bar therefore has neither its own selectable identity nor an eligible evaluation aggregate covering it. The duplication of literal role sets across renderer, scorer, MathChunk, and coverage audit remains an additional drift risk (`semanticCoverageAudit.js:29-35`).
- **Confirmed invariant — invalid progressive input fails closed and preserves only accepted work:** sequence/identity/schema violations leave reducer state unchanged; completed steps are detached and deeply frozen, drafts never enter durable state, and terminal states reject later events (`progressiveSolve.js:36-88,92-211,241-305`). UI callbacks throw on any non-accepted wire event, which cancels stream consumption; the current-operation error handler then emits the next valid `solve_failed` event and commits any already-completed steps (`PrimaryMathComposer.jsx:195-205,232-240`; `progressiveStreamClient.js:30-53`; `Home.jsx:988-1026,1110-1151`). A stale operation instead fails the component ownership check and cannot create a recovery write. No event buffering or provisional provider text is presented.
- **Confirmed invariant — progressive retry/presentation isolates attempts:** a new `solve_started` must explicitly supersede the active attempt; old identities and previous attempts cannot re-enter, while prior completed steps remain in immutable attempt history (`progressiveSolve.js:95-135,138-148`). ProblemBlock resets its per-step annotation cache and selection/presentation state by attempt id, annotates only completed steps, and preserves reader position with an explicit jump affordance (`ProblemBlock.jsx:384-412,430-511,540-549,706-729`).
