# Local persistence investigation

The fault-injection coverage in `tests/architecturePersistenceReconciliation.test.mjs` reproduces two backend behaviors with no database or external provider connection: development session create/update return the supplied session with `databaseConfigured: false` and `fallback: "missing_local_schema"` when `app_users` raises PostgreSQL `42P01`; and typed `/api/explain` returns a successful provider explanation with `saveStatus: "pending"` while the injected persistence failure is subsequently observed as `DATABASE_UNAVAILABLE`. The test's query mock rejects immediately, so it shows successful delivery despite persistence failure; by itself it does not establish the relative timing of the HTTP return and completed failure.

Static UI inspection found a separate session-save state behavior in `src/pages/Home.jsx`: lines 465–477 handle successful session-save HTTP responses by marking the session persisted and clean, including the development fallback response; line 526 sets the UI status to “Saved”. These lines concern the session-save endpoint, not the `/api/explain` solve response or its background save status. This note records the investigation only; it does not prescribe a UI or persistence architecture change.

The test mocks `pg.Pool.prototype.query`, provider responses, and usage KV calls. Clerk verification uses an offline signed JWT fixture with a generated key rather than a mocked verifier. It uses a temporary local quota path and `tests/helpers/noExternalNetwork.mjs`; it does not run SQL migrations, use a real database, or call an external provider. The command run was `node --import ./tests/helpers/noExternalNetwork.mjs --test tests/architecturePersistenceReconciliation.test.mjs` (three invocations while correcting a prompt that selected a local rule); the final run passed 2 tests with 0 failures.
