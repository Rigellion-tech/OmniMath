# Phase 6B provider streaming boundary

Phase 6A remains the sole client lifecycle and rendering authority. Provider streaming is opt-in: `VITE_PROGRESSIVE_SOLVE=true` selects it in the client, and `OMNIMATH_PROGRESSIVE_SOLVE_ENABLED=true` permits it on the server. The existing full-response request remains the default. A cached canonical answer may return the existing JSON response even when the client requested streaming; the client handles that through the full-response adapter.

Typed input and OCR-reviewed solves both enter the same shared streaming handler. The OCR adapter forwards the progressive attempt identity while retaining its review decision, image source, extraction validation, and canonical input hash as metadata. A retry sends a distinct request/attempt ID plus `supersedesAttemptId`; the server echoes that field on `solve_started` so the Phase 6A reducer can require an exact duplicate of its locally installed start event.

The server uses one-way HTTP SSE for a solve. Browser packets contain only Phase 6A events, never provider text deltas. The backend reads Responses API SSE events and frames the existing strict structured-output JSON in schema order (`title`, `problemLatex`, `steps`, `finalAnswerLatex`, `numericCheck`). A step is not a candidate until its full JSON object and array boundary have arrived. The server validates exact shape, order, IDs, required content, TeX, renderability, and canonical source identity before issuing `step_completed` with server-owned acceptance authority. The complete final JSON must match every published step; a conflicting prefix fails the attempt. Client lifecycle, stale-event, sequence, and session checks remain in the existing reducer.

The transport retains the canonical model selection, sampling, output budget, request deadline, and error translation. It retries transient connection failures only before provider bytes. Once provider output or an authoritative step is exposed, it never silently launches another solve or rewrites a completed step. Failure, timeout, cancellation, and disconnect abort the provider stream where possible. The accepted prefix remains authoritative; a partial next step stays server-only and is discarded. A failure after a prefix persists only completed steps and terminal status.

The existing overall solve timeout remains the upper bound, with the selected model's request timeout also applied. There is no additional short inactivity timer. The provider body read races against the same abort signal because a real connection was observed leaving a read pending past the deadline despite aborting the fetch. An actively streaming solve is not reset by token arrival; extending deadlines would be a separate policy decision. If the server receives terminal provider usage, it settles that usage once. If usage is absent, it does not invent token counts; it settles the provider call or releases an unused reservation according to the existing usage helpers. The legacy usage store's multi-counter settlement is not atomic, so an underlying storage failure during settlement is logged rather than retried blindly.

The streaming path does not share an in-flight SSE response through the existing completed-promise deduplicator. Each streamed subscriber is a distinct request and usage reservation. The same canonical cache remains usable once a solve fully succeeds. There is no automatic full-response fallback after streaming begins; a user retry creates a new Phase 6A attempt. This is deliberate because replacing already visible authoritative steps would create conflicting history. The existing full-response path continues to provide its own compact/repair behavior; stream-specific pre-prefix quality repair or escalation is not yet automatic.

Local deterministic integration is run with `npx playwright test --config playwright.provider-stream.config.mjs`; it uses a loopback Responses-compatible fixture, actual backend parser/validator, and actual browser SSE consumer. The separate `scripts/smoke-progressive-provider.mjs` and `scripts/smoke-progressive-browser.mjs` are optional live-provider smoke checks and are never part of the routine test suite. The loopback `OPENAI_RESPONSES_URL` override is accepted only outside production and only for a local host.
