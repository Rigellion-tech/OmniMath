# Solve response acceptance audit

This audit describes the canonical solve path as found on 2026-09-19, before the acceptance changes in this task. The working tree was already extensively modified. `server/solveCandidateStructure.js`, `server/solveCandidateLifecycle.js`, and the evidence-only verifier were present as untracked files. The findings below describe the working tree, not the last commit alone.

## Lifecycle and candidate fate

1. `server/openai.js:requestOpenAi` calls Responses with `fastSolveSchema` (or `imageSolveSchema`), which specifies required fields and shape to the provider. `parseJsonResponse` extracts the first complete JSON object, parses it, then calls `assertFastSolveResponse` or `assertImageSolveResponse`. There is no separate local JSON Schema interpreter; the assertion functions enforce the essential fields locally.
2. `server/mathExplanationSchema.js:assertFastSolveResponse` sanitizes strings and TeX, verifies required step fields, and calls `assertSolveStructureBoundary`. Compact retry uses `assertCompactSolveResponse`, with its **last step LaTeX treated as the final answer**. Image solve uses `assertImageSolveResponse` and the same structure guard.
3. `server/solveCandidateStructure.js:inspectSolveCandidateStructure` checks nonempty, visible final and step math, then invokes `validateGeneratedLatex` on them. It currently enables the strict final-answer presentation contract even when `strictParse:false` is passed by the provider assertion. `assertSolveCandidateStructure` and the schema boundary turn every finding into `AI_RESPONSE_INVALID`.
4. A parse/assertion error with `compactRetryable:true` triggers one compact provider call in `createMathExplanation`, except on image solves or when retry policy disables it. If the compact response fails, its error is thrown. The first candidate is only in error diagnostics (`invalidOutputText`, parsed JSON) and is not offered to the UI or selected as a fallback. If the first response was fully asserted, no compact retry runs. Conversion after the parse/retry block can also throw; that does not initiate an internal compact retry.
5. `convertFastSolveToMathExplanation` builds display steps, anchors, chunks, semantic tokens, lines, and final answer, then checks final-step uniqueness and structure again. `server/app.js` applies local rules and calls `assertSolveCandidateStructure`, then `finalizeSolveCandidate`, annotation, and a final structural guard. The verifier in `finalizeSolveCandidate` attaches evidence but `decideCandidateAcceptance` accepts every structurally usable candidate, even when a mathematical contradiction is reported. Hover and follow-up use the generated step, chunk, token, anchor and provenance identities after these boundaries.
6. `server/app.js:classifySolveFailure` currently classifies all errors as `response_generation_failure`. Consequently the legacy quality repair and escalation branch is not reached on this canonical route. `selectBestSafeSolveCandidate` and `compareSafeSolveCandidates` are defined but uncalled. A failed full response followed by a failed compact response yields an error, ordinarily HTTP 502, with no visible solution.

## Acceptance contract for this task

**Fatal:** No safe, complete, renderable solution can be constructed without guessing mathematics or breaking ownership. Examples: refusal, absent/incomplete/invalid JSON, explicitly truncated provider response, missing required solution or visible math, invalid required schema/step identity, unresolvable token/chunk ownership, genuinely malformed KaTeX, or a demonstrably incomplete TeX escape. Fatal findings may trigger the bounded compact retry. If every candidate is fatal, return the existing safe error.

**Recoverable:** A deterministic, meaning-preserving local operation makes the result usable: remove only outer math/Markdown wrappers, normalize known text/control-character artifacts, or repair an existing identity/reference with unambiguous ownership. Record the action, preserve the original candidate for diagnostics, and validate the resulting display math. Do not invent mathematical relationships or final values.

**Warning:** A heuristic or presentation preference cannot prove the output unusable: physical/TeX line breaks, multiple equations, systems, PDE plus conditions, branches, derivation arrows, prose in valid `\\text{}` and unusual grouping, or an unsupported mathematical verification claim. Keep the renderable candidate and log the code. Do not retry solely for a warning. An inconclusive mathematical check is not evidence of mathematical invalidity.

The central invariant is that only a fatal finding rejects a candidate. Structural checks must use the actual source field that will be rendered, preserve step and anchor ownership, and require KaTeX renderability. Mathematical evidence remains evidence-only under the current `structural-accept-v1` policy; changing its authority requires a separate policy decision.

The active `server/verification/solutionVerifier.js:verifySolution` evaluates supported claims as verified, contradicted, or inconclusive, then `server/solveAcceptancePolicy.js:decideCandidateAcceptance` accepts structurally usable responses in every case. Historical evidence: commit `b074f5b` introduced the final-answer presentation checks, trailing-backslash regex, and many quality rules together under “Harden solve validation and diagnostics.” Its new tests assert rejection of physical lines, derivation arrows, prose, and comma-separated equations; the current working tree has those tests skipped. The commit does not establish that every restriction came from a distinct production failure. Other historical regression coverage targets concrete malformed TeX, blank steps, wrong algebra, Stokes integral failures, symbols and numerical inconsistencies. Those protections should be retained where the check is sound. Later history includes `49986f9` (“removed fault validator logic”), consistent with the current evidence-only canonical policy, but the commit title alone is not proof of every rationale.

## Reproduced false positives and remaining risks

Direct `validateGeneratedLatex` calls show that valid `\\mathbb{R}^3\\ \\text{bounded and Lipschitz}` receives `trailing_backslash` because `stripTextCommands` removes the text body before scanning for a terminal slash. `x=1,\\quad y=2` and `x=1\\;y=2` receive `final_answer_contains_multiple_unrelated_equations`. `(\\Delta u,u|_{\\partial\\Omega})=(0,0)`, `aligned`, and `cases` forms pass this particular count, showing that the rule tracks punctuation layout rather than mathematical relatedness. The line-break rule does not flag all renderable `\\\\` forms consistently. A parser/render check is needed after local normalization; no regex can prove two equations are semantically unrelated.

Any candidate that fails required JSON/schema, visible math, strict KaTeX rendering, or identity ownership can still be discarded. There is no safe general fallback from a genuinely fatal original to a worse compact result without independent proof of the original's usability. Future acceptance changes should record candidate outcome, fatal/recoverable/warning codes, provider status and truncation, normalization actions, retry reason, previous usable candidate status, and selected candidate using identifiers and bounded summaries rather than logging full user prompts.

## Implemented acceptance boundary (2026-09-20)

The inventory above records the **pre-change** behavior. The current boundary separates fatal `issues`, deterministic `recoverableIssues`/normalization actions, and `warnings`. Only fatal issues make `inspectSolveCandidateStructure(...).usable` false. `createMathExplanation` now asserts, converts, and checks renderability for the full candidate inside the compact-retry boundary. A usable full candidate returns without retry; a genuinely unusable candidate can trigger the bounded compact attempt. Since no usable full candidate enters that retry branch, a later compact failure cannot displace an earlier usable one. `server/app.js` keeps its already accepted candidate if subsequent semantic decoration fails.

| Current classification | Findings and action |
| --- | --- |
| Fatal | Provider refusal, empty/unparseable JSON, explicit incomplete/truncated status, missing required schema/steps/final math, duplicate step identities, normalization that empties math, genuinely unrenderable KaTeX, structurally unmatched plain delimiters, and an incomplete fraction operand. These cannot yield a complete safe display/owner graph without guessing. |
| Recoverable | Safe wrapper removal, existing transport/escape cleanup where the source is not already renderable TeX, separate complete physical final-answer lines stacked in a `gathered` environment, and normalized field differences. Actions are recorded without another provider call. |
| Warning | Multiple related expressions (including the old `final_answer_contains_multiple_unrelated_equations` code), TeX row breaks, derivation arrows, prose probes, detached-fragment heuristics, duplicate final-answer *headings*, and lexical oddities that KaTeX renders and that do not prove incompleteness. These no longer reject a candidate. |

Renderable explicit TeX now bypasses escape collapsing in both provider normalization and semantic display preparation. This protects `\\\\` rows, spacing commands such as `\\ `, tuples, and parametric/function grouping. Raw step/final fields are checked before the repair pass so an incomplete fraction cannot be made superficially renderable by filling in a missing operand. The compact assertion retains all returned steps, including the actual final step beyond index eight. Existing anchor and step identity checks remain active; duplicate anchor IDs are made unique only where ownership is unambiguous.

Candidate outcome telemetry records bounded request/attempt/candidate identifiers, model, provider completion and truncation, normalization actions, issue classes, retry reason, and UI selection without prompts or generated equations. An opt-in, development-only canonical-input probe records the canonical `ProblemInput`, its source, the provider payload hash, and exact-text occurrence count immediately before transmission. This probe is for the separate visual-composer investigation and does not change acceptance behavior.

The 16-domain corpus covers unchanged, normalized, warned, and rejected candidates with related mathematical expressions in each domain. Focused acceptance/semantic tests passed (129/129), the corpus passed (67/67), and the clean full `npm test` passed (1,197 pass, 0 fail, 21 skip). The pre-task suite had 1,117 pass, 4 fail, 21 skip. Lint and build pass. Typecheck still reports the pre-task `src/lib/solutionState.js:143` `extractionValidation` error. Browser semantic geometry and ownership passed after updating the fixtures to the current composer; one hover lifecycle test remains reproducibly failing because its expected hover request does not appear, and a second hover check failed once but passed in isolation. The captured traces remain under `test-artifacts/`.

Remaining acceptance limits: a complete mathematical result expressed outside required schema fields still fails; unsupported KaTeX commands or unmatched plain delimiters can still reject a valid mathematical idea that the current UI cannot render safely; and an image solve has no compact retry. The current deterministic boundary does not establish whether multiple displayed equations are mathematically related or correct. The evidence-only mathematical verifier policy remains unchanged.
